# MAX7219 dot-matrix display

ESPEmu models the MAX7219 itself. It is not a generic framebuffer and not a MAX7221. The model follows the [Analog Devices MAX7219 datasheet](https://www.analog.com/media/en/technical-documentation/data-sheets/MAX7219-MAX7221.pdf), especially the serial addressing modes, the power-up section and tables 1 to 8.

## Circuit and firmware

```json
{
  "v": 1,
  "target": "esp32",
  "devices": [
    {"id": "screen", "type": "max7219", "din": 23, "clk": 18, "load": 5, "length": 4, "color": "red"}
  ]
}
```

`length` is the number of daisy-chained 8x8 modules, from 1 to 16, with a default of 1. A project can have up to eight separate chains if enough output pins are free. DIN, CLK and LOAD must be three different output pins outside the flash range. They cannot overlap other devices, except logic probes, or the I2C pins. Each chain has its own three wires, so chains cannot share an SPI bus. `color` sets the LED color in the workbench and is not a controller register. Physical inputs and scenarios cannot write display RAM.

The project creator and `make add_component` support this device. The generated `device_pins.h` defines `SCREEN_DIN_PIN`, `SCREEN_CLK_PIN`, `SCREEN_LOAD_PIN` and `SCREEN_MODULE_COUNT`. The generated documentation includes examples. The packaged driver bit-bangs real GPIO pins:

```c
#include "device_pins.h"

espemu_max7219_t screen;
ESP_ERROR_CHECK(espemu_max7219_init(&screen, SCREEN_DIN_PIN, SCREEN_CLK_PIN,
                                    SCREEN_LOAD_PIN, SCREEN_MODULE_COUNT));
const uint8_t rows[8] = {0x81, 0x42, 0x24, 0x18, 0x18, 0x24, 0x42, 0x81};
ESP_ERROR_CHECK(espemu_max7219_set_rows(&screen, 0, rows));
ESP_ERROR_CHECK(espemu_max7219_write(&screen, 0, 0x0a, 15));
```

`espemu_max7219_init` turns off decoding, scans all eight rows, sets intensity 8, clears the digit RAM, turns off display test and leaves shutdown. Every call returns an ESP-IDF error code. Check it, and do not call the driver for one chain from two tasks at once. `espemu_max7219_write` takes a register address from 0 to 15 and a data byte.

## Wire protocol

Each rising CLK edge shifts DIN, most significant bit first, into a 16-bit register. Shifting continues while LOAD is high. DOUT changes on the falling CLK edge, 16.5 clock cycles behind DIN. In a chain, each module's DOUT feeds the next module's DIN. A rising LOAD edge copies the current word into the addressed register. A falling LOAD edge leaves the shift register unchanged. Missing or extra clock pulses shift and latch exactly as the chip does. The model does not reject them as malformed. When LOAD and CLK rise together, the model shifts first and then latches.

Bits D15 to D12 are ignored, D11 to D8 select the register and D7 to D0 hold the data. Reserved registers and register 0, NO-OP, leave the RAM unchanged. Send the word for the farthest module first and the nearest module last, then raise LOAD. Module 0 is the one nearest DIN. The driver sends NO-OP words to the modules it does not target.

| Register | Behavior |
| --- | --- |
| 0x01 to 0x08 | Eight bytes of digit RAM, kept independently |
| 0x09 | Code B or no decoding for each digit. Code B uses D3 to D0 and keeps D7 as the decimal point. |
| 0x0a | The low four bits set the segment duty cycle from 1/32 to 31/32 in steps of 2/32. |
| 0x0b | The low three bits scan DIG0 through DIG0 plus n. Digits outside the scan stay blank and keep their RAM. |
| 0x0c | The low bit selects shutdown when 0 and normal operation when 1. Shutdown blanks the display and still accepts serial writes. |
| 0x0f | The low bit lights all 64 LEDs with an eight-digit scan and 31/32 duty. It overrides shutdown and the other controls without changing them. |

At power-up the control registers are zero: shutdown, one scanned digit, no decoding, minimum intensity and no display test. The datasheet leaves the initial digit and shift register contents undefined, and the model sets them to zero. A workbench reset powers the whole circuit off and on, display included. It clears the registers and the shift register and keeps the wiring.

## Display and state

The workbench draws rows DIG0 to DIG7 from top to bottom and columns D7 to D0 from left to right. Those columns are segments DP, A, B, C, D, E, F and G. Real modules may wire, rotate or mirror their LEDs differently, so transform your row bytes to match your module. Modules appear left to right in chain order and wrap on narrow screens.

On `/machine/soc/gpio`, QEMU validates the `max7219-config` property and reports the read-only `max7219-state` property. The backend checks the reported ids, wiring and module counts. Browser snapshots keep the `max7219` state separate from GPIO levels and firmware reports. Each module reports its raw `digits`, rendered `rows`, control registers, segment duty `duty32`, shift register and DOUT. Each chain counts its latches in a fixed-size counter, not an unbounded log. If the model state is missing, the workbench shows it as unavailable instead of drawing a blank display. Pause keeps the last image. A topology change restarts QEMU in a new epoch.

LED brightness in the workbench shows the average duty cycle compared with a full-intensity eight-row scan. It is not a light measurement. The model decodes GPIO edges and implements the register behavior. It does not model hardware SPI routing, setup and hold violations, the scan oscillator phase, the ISET resistor, LED current, voltage, heat or persistence of vision. DOUT links the declared modules of a chain inside the model and appears in its state. The firmware cannot read DOUT through a GPIO pin.

The demo firmware writes display RAM only when its image changes. The controller keeps the image and scans it between writes.

## Tests

`tests/qemu-models.test.ts` drives the QEMU GPIO registers directly. It checks serial edges, chain order, NO-OP, register masks, decoding, mode overrides, RAM retention and the rejection of invalid configurations. The `tests/fixtures/max7219` firmware runs single and chained displays with ordinary ESP-IDF GPIO calls and no telemetry. Runtime and browser tests check pixels, display test, shutdown, pause, reset, circuit reload and export, and desktop and mobile layouts. The ten-minute streaming test also checks that matrix latches continue and that the pixel buffers stay bounded.

```sh
bash tools/build-framework-fixtures.sh
node --import tsx --test tests/qemu-models.test.ts tests/max7219-integration.test.ts
npm run test:e2e -- --config playwright.matrix.config.ts
```

`bash tools/verify.sh` runs these checks too.
